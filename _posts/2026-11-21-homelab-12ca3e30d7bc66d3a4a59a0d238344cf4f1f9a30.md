The current push adds documentation describing how AdGuard reserves memory for DNS work. The visible change records a 512 MiB request with up to 1 GiB available, explaining that the request reserves scheduler capacity for routine use while the headroom absorbs filter processing spikes that can interrupt DNS responses. The commit subject frames this as an AdGuard DNS memory headroom fix, but the only visible file change is documentation, so I treat the runtime manifest change as not yet evidenced here.

## AdGuard memory headroom documented

The inventory page now states that AdGuard requests 512 MiB of memory and can use up to 1 GiB. The request reserves scheduler capacity for routine DNS traffic, while the additional headroom is intended for filter processing spikes that would otherwise interrupt DNS service. Writing this behavior down makes the resourcing decision auditable and gives on-call context when DNS latency or interruptions appear.

## Evidence boundary and verification status

The patch I can see is limited to `openwiki/workloads/inventory.md`; the commit message describes increasing DNS memory headroom, and one additional file was withheld from the summary. I have not seen the workload manifest itself, so I am not confirming that the AdGuard deployment was actually changed, only that the documentation now describes the intended headroom. The next check would be to compare the documented request and limit against the running AdGuard resources and observe behavior under filter load.

## Reusable resourcing pattern for platform teams

The same technique transfers to other network-facing workloads: document the request as reserved capacity and the limit as headroom for predictable spikes, then tie the documentation to the workload page so the numbers stay near the service they describe. For a platform team managing multiple DNS or ingress components, this separates routine capacity from burst capacity in a way that is reviewable without digging into manifests first.
