This push adds the Homepage image to the Harbor image catalog. The catalog is the list I reconcile deployed images against, so an image that is running but not cataloged is an image I cannot reason about during an upgrade or an audit. Three added lines in the catalog close that gap.

## Add the Homepage entry to the Harbor image catalog

The only file I changed is `scripts/config/harbor-images.json`, and the change is purely additive: a new object in the array, no removals and no edits to existing entries. The commit message describes it as cataloging the Homepage image. The sanitized excerpt elides the field values, so I can confirm the shape of the change but not restate the reference details here. Nothing in this push touches a manifest, so no workload definition changed.

## Separate the catalog edit from any deployment effect

Adding an entry to the catalog is a metadata change. It does not roll a Deployment, does not pull anything new, and does not prove that the running Homepage pod matches the cataloged reference. What this commit establishes is that the intended image is now declared in the same place as the rest of the catalog. The verification I still owe is a comparison between the catalog entry and the image the live pod actually reports, which is a runtime check rather than a code review one.

## Treat the catalog as a platform image inventory

A platform team maintaining several services on one cluster gets the same value from keeping a single declarative image inventory in Git. It makes the question of what is deployed answerable without querying every namespace, and it makes review of an image change a small, legible diff instead of a hunt through manifests. In our homelab the routine is now settled: when a component is added or its image moves, the catalog entry lands in the same pull request as the workload change, so the inventory never lags the deployment.
