This push restores protected deployment checks in CI and hardens the Uptime Kuma backup test, so our homelab pipelines validate descheduler transitions and snapshot consistency without relying on external history.

## Restore protected deployment checks in descheduler cadence check

I updated `scripts/ci/descheduler-cadence-check.sh` to render an inline Deployment YAML through `render_stage` instead of comparing rendered values against a temporary file. This lets CI exercise the descheduler transition without fetching history. The inline manifest sets `deschedulerPolicy` with `DefaultEvictor` arguments, enables `LowNodeUtilization` balancing and `RemovePodsViolatingInterPodAntiAffinity` descheduling, and applies a `deschedulingInterval` of `30m`. I also simplified the cleanup trap to remove only the rendered output file.

## Rewrite Uptime Kuma backup test around concurrent snapshot behavior

I rewrote parts of `scripts/ci/uptime-kuma-backup-test.py` to make the backup test more deterministic. The old manual threading loop was replaced with `ThreadPoolExecutor` and a `first_batch` event that drives `write_after_first_batch`, asserting that the backup copies a partial batch before additional writes occur. An `ObservedReader` class now watches the snapshot process. These changes alter test logic only; they do not represent test results, and CI still needs to run to confirm the new assertions pass.

## Protect deployment transitions and backup consistency for platform teams

This approach transfers well to platform teams that need guardrails around deployment cadence and backup reliability. Rendering an inline Deployment inside a cadence check removes dependence on external history, while snapshot tests with concurrent writers validate that backups remain consistent under load. A team operating a similar homelab could reuse this pattern to protect descheduler rollouts or verify database backups before promoting changes to production.
