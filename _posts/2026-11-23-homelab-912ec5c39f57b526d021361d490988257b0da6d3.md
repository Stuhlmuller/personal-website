A bootstrap Job that fails after several minutes usually hands me one line of log and a timeout, which is not enough to know whether Harbor was slow to become ready or whether a later policy step was the problem. In this push I added fixed phase messages to the Harbor bootstrap runner so the log itself reports where it is, and I wrote down how to read those messages when the Job gives up.

## Phase messages at the boundaries of the Harbor bootstrap run

The change is deliberately small: the bootstrap script prints a fixed progress line as it crosses each major boundary. There is a message once API readiness has been confirmed, one when project and robot policies are being checked, one when tag locks, replication, and proxy caches are being reconciled, and one when image scan and SBOM backfill is being checked. Output is flushed immediately, which matters because a Job that gets killed on deadline can otherwise buffer its last lines and lose exactly the message I need. Nothing about the reconciliation order changed. I only made the existing stages observable from the log stream.

## Reading the last phase to locate a Harbor timeout

The practical rule I documented is to read the most recent phase message and treat it as the failing stage. If the run stops before the API readiness line, the registry never came up in time. If it stops after readiness but before policy checking begins, the problem is in that handoff rather than in the registry itself. I also noted that the Harbor health endpoint is not a substitute for Job status: Harbor can report healthy while bootstrap is still working through later phases, so Job completion is the signal that the reconciliation actually finished. This push changes logging and documentation only. I have not yet captured a run that exercises a real timeout, so the next check is to confirm these messages appear in order on a clean bootstrap and that a deliberately short deadline stops between two named phases.

## Why phased bootstrap output is worth the extra prints

Bootstrap jobs tend to be the least observable part of a platform, because they run once, they run early, and they either finish or leave a partially configured system behind. Adding named phases turns a single opaque timeout into a coarse progress trace without pulling in a metrics stack, and it keeps the signal in the same place an operator is already looking. The same pattern transfers well to any team running idempotent setup jobs before a dependency: emit a fixed, greppable message at each stage boundary, flush it, and document what the last message means. It is cheap to add and it shortens the conversation during an incident from guesswork to a specific stage.
