I updated the n8n stack definition and accompanying documentation to ensure that the repaired paired checkpoint can be safely maintained, verifying exact fence revisions and backup integrity.

## Updated n8n Stack Definition for Paired Checkpoint Maintenance

The stack file `IaC/homelab/us-west-2/apps/n8n/stack.hcl` was edited with one addition and one deletion, removing a `valueFiles` reference to the n8n values. This aligns the stack with the requirement that the paired checkpoint verify the exact fence revision and that n8n is omitted from Helm `valueFiles`. By keeping the Deployment at zero replicas only when a reviewed GitOps revision is used, the stack now matches the operational expectations for the repaired checkpoint.

## Documentation Clarifies Paired Checkpoint Verification Steps

I revised `openwiki/architecture/storage-and-state.md` and `openwiki/operations/validation-gates.md` to explicitly describe the paired checkpoint verification. The architecture note now states that after the targeted `Terragrunt Apply`, the paired checkpoint must verify the exact fence revision, no n8n in Helm `valueFiles`, and that a successful live receipt binds object versions and records isolated restore. The validation‑gates document adds that the baseline values render one Deployment replica while the stack includes the overlay that renders zero, and that the checkpoint receipt verifies the live backup and isolated restore. These clarifications make the verification steps unambiguous for future maintainers.

## Transferable Practice for Platform Teams Maintaining Paired Checkpoints

The pattern of a single stack definition paired with precise documentation of verification criteria is a reusable technique. If a team is preparing maintenance for a repaired paired checkpoint in their own GitOps homelab, they can adopt the same approach: adjust the stack file to remove conflicting value files, and update the architecture and validation‑gates notes to spell out the exact checks required. This ensures that the checkpoint can reliably confirm the repaired state before the next operational cycle.
