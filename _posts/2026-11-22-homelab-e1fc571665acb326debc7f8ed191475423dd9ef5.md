This push restores the `AFFiNE` service after an earlier capacity suspension and brings the recovery notes back in line with the new active state. The merged workload changes run the application and its backing stores again, while the documentation now treats suspension as a past event rather than the current condition.

## Restore the AFFiNE Workload and Its Dependencies

I restored the `AFFiNE` deployment and brought its `PostgreSQL` and `Redis` dependencies back into service. The deployment sync wave moved later in the rollout ordering so the application could wait for the stateful components it depends on. The four existing volumes were retained, and I updated the recovery notes so they no longer describe `AFFiNE` as suspended.

## Verify the Restored Rollout and Probe Alerts

No tests were changed here, and the merged manifests still need a live rollout to count as verified. The next check is to watch the actual deployment of the restored service and confirm that the `PostgreSQL` probes report healthy results. I also updated the `Grafana` alerting so probe checks cover the affine namespace and pod alongside existing automation, media, and storage targets, and the alert groups results by namespace, pod, and container while treating missing probe totals as a failure signal.

## Carry the Recovery Pattern to Platform Teams

The technique here is to pair an explicit replica decision with retained storage and refreshed recovery notes. A platform team running similar GitOps workloads could adopt the same approach when memory pressure forces a temporary suspension and later defines a safe restore path. For our homelab the immediate next check is the rollout itself, but the design now has a documented path from suspension to restore.
