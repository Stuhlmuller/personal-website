The push adds the Bazel remote cache image to Harbor’s CI pipeline, allowing Harbor to treat Bazel cache images like any other artifact and ensuring that Bazel builds benefit from the same caching guarantees.

## Keying the Bazel cache image in the Harbor mirror workflow

I extended the options list in `.github/workflows/harbor-mirror.yml` to include `bazel-cache`, updated the case statement so the job can handle the new scope, and added a step that runs `scripts/ci/harbor-publish.sh mirror-bazel-cache --tailscale`. This makes the mirror job aware of the Bazel cache image and ensures it is fetched during the CI run.

## Policy and test updates to recognize the new image

The Rego policy `policy/workflows.rego` now includes a `bazel-cache` case in the `approved_tailnet_harbor_mirror` rule, and the corresponding test file `policy/workflows_test.rego` adds asserts that the workflow may reference `bazel-cache`. These changes keep the policy consistent with the new image scope and verify that the CI configuration is syntactically correct.

## Updated scripts and configuration to handle Bazel cache

The helper script `scripts/ci/harbor-publish.sh` was edited so its usage message lists `bazel-cache` as a supported target, and the test harness `scripts/ci/harbor-publish-test.py` now asserts that the workflow includes `bazel-cache` in its allowed image list. Additionally, `scripts/ci/offline-static-checks.sh` was tweaked to keep the same list of allowed scopes, and `scripts/config/harbor-images.json` received a new entry for the Bazel cache image.

## Verification status and next check

All code changes are merged, so the next verification step is to trigger the Harbor mirror workflow on a commit that touches a Bazel cache image and confirm that the job runs, mirrors the image, and that downstream builds succeed. If the run passes, the Bazel remote cache image will be fully enrolled in Harbor.
