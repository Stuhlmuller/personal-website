The latest main push trims the protected‑deployment workflows, removing legacy stage scripts, condensing SHA‑256 checks, and updating policy rules to discard live output streams. The change reduces surface area for sensitive data while preserving the essential guardrails for Terragrunt apply and Argo CD registration.

## Implementation: trimmed Terragrunt and policy changes

The commit fix(ci): simplify protected deployment workflows (#1971) touches several files. In .github/workflows/terragrunt-apply.yml the two‑step SHA validation was collapsed into a single line, and the nix‑cache bootstrap block was replaced with a direct `git show origin/main:scripts/config/nix-cache.json` fetch. The removed scripts/ci/terragrunt-apply-stage-test.py and scripts/ci/terragrunt-apply-stage.sh eliminated the granular phase‑and‑hint classification that previously classified each `::group::` segment. Policy rules in policy/workflows.rego now collect `quiet_deploy_runs` that umask 077 and discard both stdout and stderr, replacing the former private_live_output and private_live_tail guards. The Rego test file workflows_test.rego was stripped of the replacement‑based violation checks that once mutated apply_stage_guard and terragrunt‑apply‑stage invocations. Remaining scripts/ci/offline‑checks.sh and offline‑static‑checks.sh were adjusted to match the new permission model, dropping the `actions: read` requirement and simplifying the static‑check env list.

## Verification: pipeline lint and policy sanity checks

Because this push removes code and rewrites policy, the immediate verification step is to run the GitHub Actions lint on the changed workflow files and confirm that the Rego policies compile without errors. The withheld two files may contain additional test data, so a full test run after they are restored is recommended. A downstream check should also exercise a protected Terragrunt apply in a sandbox cluster and verify that live output is indeed suppressed and that the classifier still emits the expected phase label.

## Platform engineering: protected‑deployment pattern for platform teams

Teams that maintain GitOps pipelines can adopt the same simplification strategy: collapse redundant SHA checks into a single line, replace bootstrap blocks with direct origin fetches, strip per‑phase classification scripts when coarse‑grained exit‑status guards suffice, and centralize output‑discarding logic in policy rather than inline shell. The result is a smaller attack surface for secrets and easier on‑call debugging because the workflow’s failure mode is a single exit code rather than a cascade of hint labels. A homelab or enterprise platform can register this pattern in its internal CDK and reuse it for any CI system that supports policy‑as‑code guards.
