The Harbor mirror workflow now supports a dedicated n8n image scope, so n8n can be published and verified as an independent versioned digest instead of being bundled into the shared Renovate mirror batch. I wired that scope through the workflow, policy, publish scripts, documentation, and tests, and added a small configuration file that describes the n8n image set.

## Add a dedicated n8n case to the mirror workflow

The Harbor mirror workflow now recognizes n8n as its own image scope. The job dispatch options and the validated scope list both include n8n, and the workflow routes a n8n request to the dedicated publish path. This keeps the n8n publication concern separate from the larger Renovate batch while still reusing the existing mirror machinery.

## Route n8n through the dedicated mirror publish command

The publish helper now accepts a mirror n8n action and forwards it to the mirror-n8n entry point with the tailscale flag. The policy layer mirrors the same branching so approved mirror scopes stay explicit and fail closed. I also updated the publish helper tests to cover the new scope, including the expected workflow token list.

## Document the independent n8n publication flow

The Harbor operations notes and the mirroring guide now point readers to the n8n mirror scope for staged n8n image publication. That scope verifies a complete authenticated Harbor pull independently of the shared Renovate batch, which gives us a clearer verification boundary for n8n releases.

## Consider the pattern for other independent images

The same split between a shared batch and a single-image scope could transfer to other services that need isolated publication and verification. A platform team could adopt this approach when a workload should not inherit the operational risk of a large batch, or when its release cadence deserves a distinct digest and validation path.
