This push removes the staged hourly application backup scheduler end to end: the runner script, its schedule config, the doc sections that defined its activation gates, and the tests that exercised it. The repository no longer advertises an automated off-NAS publication pipeline that was never activated, and the runbook now describes the off-NAS publisher as a manual recovery tool backed by the shared S3 destination.

## What the removal deletes

The commit removes `scripts/application-backup-run.py` and `recovery/application-backups/schedule.json`. The runner had selected the newest completed local backup set, enforced a free-space floor on private scratch, and refused to fall back to a stale set; those behaviors leave with it. `docs/application-recovery.md` loses far more lines than it gains, dropping the retention-plan prose and the section on exact proposed resources and authorization gates; the excerpt I read shows only deletions, so I cannot yet characterize the small number of added lines. Two wiki pages align the story: `openwiki/architecture/storage-and-state.md` now credits the shared S3 destination and manual publication commands for independent recovery, and `openwiki/workloads/inventory.md` calls the off-NAS publisher a manual recovery tool.

## Test deletions are code changes, not results

`scripts/ci/application-backup-test.py` drops 34 lines with no additions: fixture tests that loaded the runner module, wrote a fixture schedule, patched the runner root and cloud client, and covered both a successful run and a failed copy. `scripts/ci/offline-checks.sh` loses one line, consistent with retiring the deleted runner test, though the excerpt I read does not show that line. I have not run the suite here, so these are edits to tests, not test outcomes. The next check is to run the offline checks and search the tree for stale references to the runner or its schedule config before treating the removal as complete.

## When to delete a staged automation instead of finishing it

The lesson I take is that a candidate automation with explicit activation gates can outlive its justification if the gates are never met. Removing runner, config, gate prose, and tests in one commit keeps the docs from promising a mode that does not ship, while the manual publication path stays available and documented. A platform team maintaining a half-built offsite snapshot job that never cleared freshness or approval gates can use the same move: delete the scheduler, shrink the harness to the tool that actually ships, and rewrite the runbook so operators rely on manual publication rather than an automatic capture they will never get.
